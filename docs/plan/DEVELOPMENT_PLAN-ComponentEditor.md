# Component Designer development plan

Status: proposed  
Source of truth: [`docs/BLUEPRINT-ComponentEditor.md`](../BLUEPRINT-ComponentEditor.md)  
Related source: [`docs/BLUEPRINT.md`](../BLUEPRINT.md)  
Scope: live component viewer first, followed by graphical and LLM-assisted
component authoring

## 1. Outcome and delivery strategy

The first independently releasable outcome is a read-only Component Designer
mode that opens a user-selected component directory, validates
`component.toml`, renders it on a 2.54 mm grid, and refreshes when the file
changes on disk. It provides the visual verification needed for definitions
written by hand or generated by an LLM without first building a graphical
editor.

Later milestones add graphical editing, safe persistence, library/project
upgrade workflows, templates, and equivalent MCP operations. Each milestone
must leave a runnable and tested vertical slice.

The main architectural rule is:

> One Rust component model and validator serve runtime loading, preview,
> graphical editing, library use, project upgrades, and MCP authoring. The
> frontend renders and interacts with that model but does not redefine it.

## 2. Boundaries and initial decisions

### Included

- An integrated top-level Component Designer mode.
- Runtime loading from explicitly selected component-library roots.
- A read-only live viewer with manual reload and debounced file watching.
- Last-known-good preview behavior and actionable diagnostics.
- Component geometry, rotation, pin metadata, helper features, and sanitized
  Markdown inspection.
- Later graphical authoring through typed operations.
- Safe save, versioning, explicit project-definition upgrades, templates, and
  MCP parity.

### Explicitly deferred

- Arbitrary vector artwork and decorative labels.
- Free-angle rotation, arbitrary pin pitch, 3D rendering, and mechanical CAD.
- Automatic extraction from datasheets or images without review.
- Cloud component libraries and network collaboration.
- Silent library replacement or automatic project snapshot upgrades.
- Electrical correctness guarantees based on pin metadata.

### Initial technical decisions

| Area | Initial choice | Reason |
|---|---|---|
| Product structure | A mode inside the existing Tauri application | Shares the model and renderer while allowing an independent UI. |
| First release | Read-only file-backed viewer | Immediately supports manual and LLM authoring with low write risk. |
| Authority | Rust parser and validator | Prevents frontend and MCP behavior from drifting. |
| Preview | SVG derived from validated structured data | Matches the existing board renderer and remains testable. |
| Labels | Generated component and pin labels plus structured feature labels | Keeps labels attached to semantic geometry. |
| Watch scope | Only the selected component directory | Limits permissions and lifecycle complexity. |
| Error state | Preserve and mark the last valid preview | Keeps the visual reference while accurately reporting invalid disk state. |
| Persistence | No writes until the graphical-authoring milestone | Separates safe inspection from replacement and conflict semantics. |
| Project compatibility | Immutable embedded snapshots with explicit upgrades | Library changes cannot silently alter saved projects. |

The live viewer does not require a component schema revision. A schema change
must be justified by a concrete definition that existing body, pin, occupied
hole, keepout, or access data cannot represent.

## 3. Shared contracts

### 3.1 Viewer state

Model the frontend-visible viewer state explicitly rather than inferring it
from nullable fields. It must distinguish:

- No component open.
- Loading.
- Current valid preview.
- Last-known-good preview with an invalid on-disk revision.
- Load failure with no valid preview.
- Watcher unavailable or stopped.

A successful load includes the validated definition, optional sanitized or raw
untrusted Markdown payload, canonical component path identifier, and a content
revision or hash suitable for detecting stale saves later.

### 3.2 Runtime load boundary

Runtime component loading:

- Accepts only a directory selected beneath an authorized library root.
- Resolves and verifies paths before reading.
- Reads `component.toml` and optional `README.md`.
- Parses and validates in Rust.
- Returns structured diagnostics without mutating application state outside the
  viewer session.
- Does not add the definition to the placement palette in the first release.

Transport command and event names may follow repository conventions and are
not serialized domain contracts. Their responses must remain typed and
contract-tested between Rust and TypeScript.

### 3.3 Reload and watcher behavior

- Manual reload and filesystem events use the same load pipeline.
- Events are debounced; the final state of a save burst is loaded once.
- Rename-and-replace saves are supported by watching the directory rather than
  assuming the original file handle remains valid.
- A failed reload publishes diagnostics and stale state but does not discard
  the previous validated definition.
- Opening another component cancels the prior watcher before starting a new
  one.
- Watcher events carry enough identity to ignore late events from a component
  that is no longer active.

### 3.4 Rendering and labels

- Use the definition's local integer grid for pins and occupied holes.
- Convert millimetre body geometry using the same pitch rules as board
  rendering.
- Share component render primitives with the board renderer where practical;
  otherwise require fixture-based equivalence tests.
- Generate component, pin, and structured feature labels from authoritative
  fields.
- Keep full pin metadata available in a table even when canvas labels are
  hidden or abbreviated.

## 4. Milestone plan

### Milestone CE0 — Contracts, fixtures, and render foundation

Goal: establish stable viewer states and rendering behavior before adding
filesystem lifecycle code.

Domain and adapter work:

- Define typed runtime-load results, diagnostics, viewer state, and content
  revision/hash behavior.
- Keep the existing `ComponentDefinition` and component-v1 TOML format
  authoritative.
- Identify and extract reusable component-rendering logic, or add equivalence
  tests between the standalone preview and board rendering.
- Ensure parse diagnostics preserve useful source locations when available.

Frontend work:

- Add the top-level mode switch and an empty Component Designer workspace.
- Implement a standalone preview from validated in-memory fixture data.
- Add fit, zoom, pan, rotation, overlay, and pin-label controls.
- Add the pin table and synchronized canvas/table selection.

Fixtures and tests:

- Reuse the Nano-like and RS485 definitions.
- Add an asymmetric rotated fixture, a dense pin-label fixture, and invalid TOML
  and validation fixtures.
- Cover negative overhang, occupied holes, keepouts, access directions, and all
  label modes with unit and visual tests.

Exit criteria:

- The Component Designer mode renders validated fixture definitions without
  accessing disk at runtime.
- Pins align exactly to the visible grid in every allowed rotation.
- The pin table exposes complete metadata and stays synchronized with canvas
  selection.
- The perfboard and preview renderers agree on component geometry for permanent
  fixtures.

### Milestone CE1 — Runtime file-backed viewer

Goal: open and explicitly reload a component directory without mutating it.

Rust and Tauri work:

- Add user-mediated selection of a component directory or approved library
  root using the application's filesystem permission model.
- Add the read-only runtime loader for `component.toml` and optional
  `README.md`.
- Canonicalize paths and reject access outside the selected root, including
  symlink escapes.
- Return structured parse and validation diagnostics.
- Track a deterministic content revision/hash for the loaded files.

Frontend work:

- Add Open Component, Close, and Reload actions.
- Render current, loading, no-component, and load-error states.
- Show component identity, definition version, description, allowed rotations,
  geometry, pin table, and sanitized documentation.
- Make clear that this milestone is read-only and does not add the definition
  to the placement library.

Tests:

- Opening valid and invalid directories.
- Missing `component.toml`, missing optional README, malformed TOML, and
  validation failures.
- Permission-root and symlink escape cases.
- Repeated explicit reload and resource cleanup.
- Markdown sanitization and absence behavior.

Exit criteria:

- A user can select either bundled example directory at runtime and see the
  same validated geometry expected from its source file.
- Invalid content produces actionable diagnostics without a crash or write.
- No viewer action changes a component file, library palette, active project,
  or embedded project definition.

### Milestone CE2 — Reliable live reload

Goal: update the preview safely when an external editor changes the component
files.

Backend work:

- Add a scoped directory watcher with a lifecycle owned by the active
  Component Designer session.
- Debounce event bursts and route watcher refreshes through the CE1 loader.
- Handle in-place writes, create/delete events, and rename-and-replace saves.
- Tag events with the active component identity/generation so late events from
  a closed watcher are ignored.
- Publish watcher status and load results through typed events.

Frontend work:

- Refresh the preview automatically after a valid change.
- Preserve and visibly mark the last-known-good preview after an invalid
  change.
- Show the attempted load time or revision, watcher status, and current
  diagnostics.
- Recover automatically when a later edit becomes valid.
- Retain the manual Reload action as a fallback.

Tests:

- Debounced multi-event writes and rapid consecutive saves.
- Rename-and-replace behavior representative of common editors.
- Valid-to-invalid, invalid-to-valid, file deletion, and file recreation.
- Switching components while events are queued.
- Watcher start/stop cleanup and application shutdown.
- End-to-end external edit demonstration in the desktop application.

Exit criteria:

- Editing `component.toml` externally updates a valid preview without an
  application restart.
- An invalid intermediate save never replaces the last validated definition.
- The UI accurately distinguishes current and stale preview states.
- File watching never expands access beyond the selected root.

CE2 is the first Component Designer release target.

### Milestone CE3 — Graphical component authoring

Goal: edit a component draft graphically and save it without corrupting the
library or overwriting concurrent external work.

Domain and operation work:

- Define typed operations for component metadata, body, rotations, pins,
  occupied holes, keepouts, access regions, and documentation.
- Apply every mutation through Rust validation and return normalized changes
  and diagnostics.
- Add component-draft undo/redo and explicit valid, invalid, and dirty state.
- Define stable TOML serialization that preserves authoritative meaning and
  produces reviewable output.

Frontend work:

- Add form and direct-manipulation controls for the supported fields.
- Snap pins and occupied holes to the integer grid.
- Keep the preview live while editing and make invalid draft geometry visible.
- Support keyboard editing and accessible alternatives for canvas gestures.
- Do not add unrestricted drawing or arbitrary text tools.

Persistence work:

- Require an explicit Save or Save As action.
- Detect content changes since load and report a conflict rather than silently
  overwriting them.
- Write to a sibling temporary file, flush, validate the written result, and
  atomically replace where supported.
- Retain a recoverable backup for replacement and document recovery behavior.
- Update the definition version or canonical content hash explicitly.

Tests:

- Operation validation and undo/redo sequences.
- Pin snapping and duplicate identity prevention.
- Deterministic TOML serialization and round trips.
- Atomic save, failed save, backup recovery, and external-edit conflict.
- Keyboard and graphical interaction parity.

Exit criteria:

- A user can create or revise the supported component fields, preview every
  allowed rotation, undo changes, and save a definition that reparses
  identically.
- Concurrent external changes are never silently overwritten.
- Saving a library component does not alter any open or saved project.

### Milestone CE4 — Library and project upgrade workflow

Goal: manage authored definitions in the placement library and adopt revisions
in projects explicitly.

Library work:

- Add create, duplicate-as-variant, rename-display-metadata, and delete or
  archive workflows with stable-ID collision checks.
- Refresh the placement palette only through an explicit, validated library
  refresh operation.
- Distinguish stable definition identity from directory name and display name.

Project work:

- Detect when an instance's embedded definition differs from a selected
  library revision.
- Produce a semantic upgrade preview for pins, geometry, rotations, keepouts,
  access regions, and resulting project diagnostics.
- Apply an accepted upgrade through the project operation/revision system.
- Preserve the former snapshot in history and support normal undo/restore.
- Reject or require explicit resolution for removed pins that are referenced by
  nets or wires.

Tests:

- Stable-ID and version collisions.
- Library refresh after valid and invalid replacements.
- Geometry-only, metadata-only, added-pin, moved-pin, and removed-pin upgrades.
- Routes and nets referencing changed pins.
- Upgrade undo, commit, save/reopen, and historical rendering.

Exit criteria:

- A revised definition can be made available for new placements without
  modifying existing instances.
- The user can preview and explicitly accept or reject an instance upgrade.
- No library file change silently changes project geometry or connectivity.

### Milestone CE5 — Templates and variants

Goal: create common through-hole components efficiently without weakening the
ordinary component-definition contract.

Template work:

- Add constrained generators for axial resistors, axial diodes, radial
  capacitors, LEDs, transistor packages, pin headers, and DIP/socket packages.
- Start with a small set of clearly named size presets; add arbitrary parameters
  only when a demonstrated component requires them.
- Generate normal component drafts that can be reviewed and edited before
  saving.
- Require explicit lead ordering and function metadata for package variants
  whose physical appearance does not determine pinout.

Tests:

- Golden definitions for every preset.
- Pin span, body dimension, orientation, and label checks.
- Variant identity and serialization round trips.
- Explicit transistor and polarized-part orientation cases.

Exit criteria:

- A user can generate the agreed common families, inspect the ordinary draft,
  customize metadata, and save it through the CE3 workflow.
- Templates do not introduce a second component type or hidden runtime
  geometry.

### Milestone CE6 — LLM and MCP authoring

Goal: allow an external MCP client to propose component changes using the same
operations and safeguards as the graphical editor.

MCP work:

- Add read tools for the active component draft, diagnostics, preview, and
  documentation.
- Add proposal-oriented authoring operations equivalent to CE3 operations.
- Restrict reads and writes to user-selected component-library roots.
- Require expected content revision/hash for replacements.
- Return normalized definitions, diagnostics, affected fields, and previewable
  changes.
- Require explicit user acceptance before saving or replacing an existing
  definition.

Tests:

- Direct Rust, Tauri, and MCP operation equivalence.
- Stale-content conflicts between external edits, UI edits, and MCP proposals.
- Path-boundary, malformed request, and unauthorized replacement cases.
- End-to-end LLM draft, validation failure, correction, preview, and accepted
  save.

Exit criteria:

- An MCP client can draft or revise a component without bypassing Rust
  validation, filesystem boundaries, preview, or explicit acceptance.
- A human can review the exact proposed geometry and pin metadata before any
  library replacement.

### Milestone CE7 — Release hardening

Goal: make the complete Component Designer dependable on supported desktop
platforms.

Work:

- Complete keyboard navigation, accessible announcements, focus behavior, and
  non-color status cues.
- Test watcher behavior and atomic replacement on every supported platform.
- Add corrupt-file, interrupted-save, backup-restoration, and permission-change
  recovery guidance.
- Profile dense but realistic definitions such as two-row controller modules.
- Add onboarding, component-authoring documentation, and warnings that
  validation does not prove datasheet accuracy or electrical safety.
- Audit all blueprint acceptance criteria in packaged builds.

Exit criteria:

- Every acceptance criterion in the component-editor blueprint has an
  automated test, documented manual test, or both.
- Packaged builds complete open -> watch -> diagnose -> edit -> save -> library
  refresh -> explicit project upgrade.
- Known platform limitations and safety boundaries are documented.

## 5. Test strategy

### Test layers

1. **Core tests:** parsing, validation, operations, rotations, and deterministic
   serialization.
2. **Filesystem tests:** authorized roots, canonical paths, optional files,
   symlinks, atomic replacement, and backups.
3. **Watcher tests:** debouncing, save strategies, lifecycle, and stale-event
   rejection.
4. **Adapter contract tests:** equivalent typed results through direct Rust,
   Tauri, and later MCP paths.
5. **Frontend tests:** state transitions, controls, pin-table synchronization,
   diagnostics, and accessibility.
6. **Visual tests:** geometry, overlays, rotations, dense labels, stale preview,
   and invalid states.
7. **End-to-end tests:** external text edit for CE2 and the complete graphical
   authoring and project-upgrade flow for later milestones.

### Permanent fixtures

- Arduino Nano-like two-row module with overhang and USB access.
- RS485 breakout with directional access.
- Asymmetric component exercising every allowed rotation.
- Dense pin layout exercising every label mode.
- Generic two-pin axial part.
- Polarized and transistor-package variants with explicit orientation.
- Invalid TOML, unsupported schema, duplicate pin, invalid body, and invalid
  region cases.
- Older project snapshot paired with a changed library definition.

### Quality gates

Every implementation change should pass:

- Rust formatting, linting, and tests.
- TypeScript formatting, type checking, tests, and production build.
- Component format and serialization round-trip tests.
- Permission-boundary tests for filesystem changes.
- Intentional review of changed visual goldens.
- Save/reopen or reload verification appropriate to the milestone.

## 6. Implementation sequence within a milestone

Use this order for reviewable vertical changes:

1. Update the contract and permanent fixtures.
2. Add failing Rust tests for authoritative behavior.
3. Implement the core type, operation, loader, or watcher behavior.
4. Expose typed Tauri responses or events.
5. Update and contract-test the TypeScript interface.
6. Add the smallest usable frontend interaction.
7. Add integration, visual, accessibility, and permission coverage.
8. Demonstrate the milestone with a bundled component.
9. Document limitations before marking the milestone complete.

## 7. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Preview and board rendering drift | Share primitives or require fixture-based equivalence tests. |
| Watcher sees partial or duplicate saves | Debounce directory events and validate a coherent reread before publishing. |
| Invalid edits destroy useful context | Preserve and clearly mark the last-known-good preview. |
| Watchers leak or deliver stale events | Scope them to an active session generation and test teardown. |
| Runtime file access becomes too broad | Require selected roots, canonicalize paths, and reject symlink escapes. |
| Canvas labels become unreadable | Offer label modes, selection details, and an authoritative pin table. |
| Frontend duplicates validation | Keep rules in Rust and return structured diagnostics. |
| Graphical saves overwrite external work | Compare the loaded content revision/hash before atomic replacement. |
| Library edits break projects | Preserve embedded snapshots and require explicit upgrade operations. |
| Templates imply incorrect pinouts | Require explicit variants and lead ordering; never infer from package shape. |
| LLM output looks plausible but is wrong | Validate structure, show a preview, require human confirmation, and warn about datasheet verification. |
| Scope expands into vector CAD | Restrict graphics to structured component features tied to functional geometry. |

## 8. Decision checkpoints

- **CE0:** choose renderer extraction versus equivalence-tested standalone
  renderer after a small refactor spike.
- **CE1:** choose the Tauri directory-selection and scoped permission mechanism
  supported by packaged targets.
- **CE2:** choose the watcher dependency and debounce policy after testing
  in-place and rename-and-replace saves on supported platforms.
- **Before CE3:** define stable TOML serialization, external-edit conflict
  semantics, version/hash policy, and backup retention in an ADR.
- **Before CE4:** define pin-removal and pin-identity migration policy for
  project upgrades.
- **Before CE5:** select the smallest useful preset catalog from real component
  examples.
- **Before CE6:** define proposal acceptance and library-write authorization in
  the existing MCP session security model.

No checkpoint should block earlier work whose contracts do not depend on the
decision.

## 9. Definition of done

The live viewer release is done when an external edit to a selected
`component.toml` is parsed, validated, and accurately previewed without restart;
invalid edits retain a clearly stale last-valid preview with actionable
diagnostics; and no viewer action mutates the library or a project.

The complete Component Designer is done when a human or MCP client can create
or revise a component through the same Rust operations, preview and validate
it, save it safely with conflict protection and explicit versioning, make it
available for new placements, and deliberately upgrade an existing project
without silent geometry or connectivity changes.
